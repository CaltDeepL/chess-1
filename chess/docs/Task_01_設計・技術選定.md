# task-01 設計・技術選定

## ゴールと完了条件
- 実装範囲(バックエンド/フロントエンド)を洗い出し、ライブラリに任せる範囲を確定する
- 認証方式・WebSocket認証方式・コード構成の方針を決める
- 完了条件: 最小構成の実装順序と必要クレート一覧が確定していること

## 設計判断の根拠
| 判断 | 根拠 |
|---|---|
| チェスルールは `shakmaty` に一任 | `chess` クレートより機能が豊富でメンテナンスも活発。ルール実装は本質的な学習対象ではないため車輪の再発明を避ける |
| プレイヤー識別はJWT認証 | 匿名セッションでは対局履歴・棋譜をユーザーに紐付けられない。実務で使われる方式を学ぶ意図もある |
| WebSocket認証は接続後の最初のメッセージで送信 | ブラウザのWebSocket APIは任意ヘッダーを送れない。クエリパラメータ方式はURLやアクセスログにトークンが残るため不採用 |
| 引き分け提案機能は実装しない | ステイルメイト等のルール上の引き分けは `shakmaty` の判定結果として残せば足りる。対話的な提案・受諾フローは状態管理が増える割に学習効果が薄い |
| `main.rs` 単一構成から始める | 最初からモジュールを切ると、どこに何を置くべきかが実装前には決めきれない。動くものを作ってから構造を整える方針 |

## 実装順序(確定)
1. Axumで最小サーバー(`/health` のみ)
2. `shakmaty` を組み込み合法手判定だけ動かす
3. ゲームセッション管理(メモリ上)
4. WebSocketエンドポイント
5. フロントエンドを本格実装し3・4とつなぐ

## つまずいた点と教訓
- 当初 `app.rs` / `game/{session,manager,message}.rs` / `error.rs` という細かいモジュール構成を設計したが、実際には `state.rs` / `models.rs` / `auth.rs` に統合する形に落ち着いた
- **教訓**: 実装前のディレクトリ設計は「あたり」でしかない。実装しながら必要になった単位で切るほうが、空ファイルや責務のない層を作らずに済む

## 次タスクへの引き継ぎ
- 最小クレート構成は `axum` + `tokio` + `shakmaty` + `serde/serde_json` + `uuid` の5点セットから開始する
- DB・認証系クレート(`sqlx` / `argon2` / `jsonwebtoken`)は task-03 以降で追加する

## 再現コマンド
```bash
cargo new chess --bin
cd chess
cargo add axum tokio --features tokio/full
cargo add shakmaty serde serde_json uuid --features serde/derive,uuid/v4
```
