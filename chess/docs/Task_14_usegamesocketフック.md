# task-14 useGameSocketフック(WebSocketクライアント)

## ゴールと完了条件
- WebSocket接続の確立・認証・イベント購読・自動再接続を担うカスタムフックを作る
- 完了条件: 接続で `open`、サーバー強制停止で `reconnecting`、復旧で自動的に `open` へ戻ること

## 設計判断の根拠(分離設計の採用)
**このフックは接続管理と生イベントの中継に専念し、盤面state(FEN/turn/result)の更新は `GamePage.tsx` 側で行う。**

検討した2案:
| 案 | メリット | デメリット |
|---|---|---|
| A: フックは生イベントのみ返す(**採用**) | 責務が単純でテストしやすい。`GameEvent` の種類が増えてもフックは変更不要。生データの流れが見えるので学習効果も高い | `GamePage.tsx` が肥大化しやすい。将来の観戦画面などで再利用しづらい |
| B: フック内でFEN管理まで行う | 呼び出し側がシンプルになる。再利用しやすい | 「接続管理」と「ゲーム状態管理」の2責務を持つ。イベント追加のたびに内部の `switch` を触る必要がある |

**採用理由**: ①対局画面以外での再利用予定が今のところない ②生イベントとゲームロジックを分けたほうがテストしやすい ③責務を単純にしたほうが型不一致バグを見つけやすい(このプロジェクトで頻発しているため)。再利用が必要になった時点で `useChessGame` として切り出す2段階リファクタ方針とする。

## 実装内容
- `gameId` / `token` を受け取り接続、`onopen` で `{"token": "..."}` を送信して認証
- 受信メッセージをパースし `lastEvent` として公開(ゲームロジックの解釈はしない)
- ステータス: `connecting` / `reconnecting` / `open` / `closed` / `error`
- `onclose` 時に**指数バックオフで再接続**(1秒→2秒→4秒…最大30秒)。`stopped` フラグでアンマウント/依存値変更時のクリーンアップと意図しない再接続を区別。接続成功時に試行回数をリセット
- `api/client.ts` に `WS_BASE_URL`(`BASE_URL` の http→ws 変換)と `wsUrl(path)` を追加して共有化

## つまずいた点と教訓
- 当初ステータスは `connecting` のみで、**初回接続中と再接続中を区別できなかった**。UI側で「接続が切れました。再接続しています」と出したいケースがあり、`reconnecting` を後から追加した
- **教訓**: 状態を表す列挙は「今の実装で区別できるか」ではなく「**UIが区別して見せたいか**」で設計する

## 次タスクへの引き継ぎ

