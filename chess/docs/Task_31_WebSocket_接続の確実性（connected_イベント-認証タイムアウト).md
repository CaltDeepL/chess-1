# task-31 WebSocket 接続の確実性（connected イベント / 認証タイムアウト）

## ゴールと完了条件
- 接続状態の表示を「TCPが繋がった」ではなく「**購読が始まった**」に合わせる
- 認証メッセージを送らないクライアントがタスクを保持し続ける問題を塞ぐ
- 完了条件: テストの時間待ちが消え、フロントの接続LEDが実際の購読完了を反映すること

task-30 の引き継ぎに書いた2項目を消化するタスク。バックエンド・フロント・テストの3層が同時に良くなる。

## 実装

| 対象 | 内容 |
|---|---|
| `src/routes/ws.rs` | `subscribe()` 直後に `{"type":"connected"}` を**新規接続にのみ直接送信** |
| `src/routes/ws.rs` | 認証メッセージ待ちの `recv()` を `tokio::time::timeout(10秒, ...)` でラップ |

| `src/hooks/useGameSocket.ts` | `onopen` ではなく `connected` の受信で `status` を `"open"` にする |

## 設計判断の根拠

### なぜ broadcast ではなく直接送信なのか
`connected` は「**あなたの購読が始まった**」という個別の確認応答であり、対局に起きた出来事ではない。broadcast に流すと既存の接続者全員に他人の接続が通知されることになり、意味が変わる。チャネルは「対局のイベント」だけを運ぶ、という役割分担を保った。

### なぜテストの時間待ちを消せるのか
task-30 では `connect_ws` に 200ms の `sleep` を入れて購読開始を待っていた。これは**環境が遅ければ不足しうる**タイミング依存で、CI で稀に落ちる類の不安定要因になる。

`connected` があれば「サーバーが購読を終えたこと」をテストが**直接観測できる**ため、待ち時間の見積もりが不要になる。時間で誤魔化していた同期を、明示的な合図に置き換えた形。

### なぜ接続LEDの緑が遅れてよいのか
変更前は `onopen`（TCP + upgrade 成功）で緑にしていたが、このアプリの認証は upgrade 後の最初のメッセージで行う（task-30 参照）。つまり**認証に失敗する接続でも一瞬緑になっていた**。

`connected` を待つと緑になるまでが数十ms遅れるが、その間は「接続中」の表示であり誤りではない。**一瞬でも誤った状態を見せるより、正しい状態に遅れて到達するほうがよい。**

### なぜ認証待ちにタイムアウトが要るのか
変更前は最初の `recv()` に上限が無く、接続だけして何も送らないクライアントが `handle_socket` のタスクを保持し続けた。認証前なので参加者チェックも通っておらず、**誰でも無制限にタスクを積める**状態だった。Render の無料枠で動かす前提では特に避けたい。

10秒は「正規のクライアントが `onopen` 直後に送るには十分すぎる一方、放置された接続を長く抱えない」線として設定。

## テストしないことにした項目

10秒タイムアウトが実際に発火することの自動テストは**追加していない**。実行に10秒以上かかり CI 全体を遅くするため。

`tokio::time::pause()` で仮想時間を進める方法もあるが、`#[sqlx::test]` が実際の DB I/O を伴うため素直には効かない。必要になれば `#[ignore]` 付きの手動実行用テストとして足せる。

**教訓**: 「テストできる」と「テストする価値がある」は別。見送った場合は、その判断と理由を残しておけば、後から見て「書き忘れ」と区別できる。
