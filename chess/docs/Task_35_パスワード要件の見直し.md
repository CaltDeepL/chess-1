## 設計判断の根拠

### 文字種を強制しない
NIST SP 800-63B の方針に沿う。文字種を強制すると `Password1!` のような、**覚えにくいわりに破られやすい**パスワードに誘導してしまう。長さで強度を担保し、パスフレーズを許可するほうが合理的。

最小を12にしたのは、文字種を強制しないぶんを長さで補うため。NIST の推奨は8だが、8文字で文字種の制約も無いと弱すぎる。

### 既存の問題を2つ修正した

**バイト数で数えていた。** `payload.password.len()` はバイト数を返すため、「正しい馬の電池」（7文字・21バイト）が8バイト制限を通過していた。日本語話者が短いパスワードを設定できてしまう状態だった。`chars().count()` に変更。

**上限が無かった。** 1MB のパスワードを送られると Argon2 のハッシュ化でサーバーが詰まる。Argon2 は意図的に重い処理なので、**入力長の上限が無いことがそのまま DoS の入口**になる。128文字で打ち切る。

### `login` を変更しない
2つの理由がある。

**1. 既存ユーザーが締め出される。** 最小を12に上げたあと `login` でも検証すると、8〜11文字で登録済みのユーザーが自分のアカウントに入れなくなる。要件の変更は「これから作るパスワード」に適用するもの。`existing_short_password_can_still_log_in` でこれを守る。

**2. 情報が漏れる。** `login` で「パスワードが短すぎます」と返すと、送った文字列が保存されているものと一致するかに関わらず、要件を満たさないことが分かってしまう。ログインの失敗は常に同じ 401 にすべき。

### 長さを拒否リストより先に判定する
短くて かつ ありふれたパスワード（`password`）には、まず「短い」と伝える。「よくあるパスワードです」と言われて別の短いものに変えても、また弾かれて往復が増える。

### エラー文言に「どうすればよいか」を含める
「パスワードが不正です」だけでは直しようがない。必要な文字数を示し、**記号や数字が必須でないことも明記する**。文字種を強制しない方針は利用者にとって直感に反するので、伝えないと `Password1!` 系を試し続けることになる。

### 拒否リストを自前で持つ範囲
22件の最小限に留めた。網羅性は目的ではなく、最頻出のものを弾くだけ。**自前の巨大な辞書を手で維持するのは割に合わない**ので、本格的にやるなら外部の仕組みに寄せる（引き継ぎ参照）。

### `/problems/validation` を新設しなかった
計画にあった案だが、`AppError` の全変種に影響する変更になる。task-28 で「フロントが実際に分岐したくなった箇所だけ後から細分化する」方針にしており、**現状フロントは `detail` を表示するだけ**で分岐していない。

もしフォームの該当フィールドをハイライトしたくなったら、`type` の細分化ではなく **RFC 9457 の拡張メンバー**として `errors: [{field, detail}]` を足すほうが適切。`type` は問題の種類であって、どのフィールドかという情報ではない。

## つまずいた点と教訓

要件の引き上げにより既存テスト5件が壊れた。いずれもテストの意図は変えず、値の差し替えと検証漏れの補完で対応した。

| # | 箇所 | 原因 |
|---|---|---|
| 1 | ビルドが通らない | `src/domain/mod.rs` に `pub mod password;` の宣言漏れ |
| 2 | `auth_test.rs` 3件 | `"password123"`（11文字）が新要件で弾かれた |
| 3 | `auth_test.rs` `login_with_wrong_password_returns_401` | **緑のまま意味を失っていた**（下記） |
| 4 | `problem_details_test.rs` `conflict_returns_problem_details` | 1回目の登録が400になり、2回目も409ではなく400 |
| 5 | `ws_test.rs` `setup_game` | ユーザー名に UUID 全体（36文字）を使っており、新設した32文字上限に抵触 |
| 6 | clippy | doc コメントが分断され `empty_line_after_outer_attr` に抵触 |

### 教訓1: セットアップの失敗を assert していないと、テストが静かに意味を失う（#3）

`login_with_wrong_password_returns_401` は**通り続けていた**が、検証しているものが変わっていた。

```
事前登録（"password123"）→ 400 で失敗 → "alice" は存在しない
        ↓
「aliceに誤ったパスワードでログイン」のつもりの操作
        ↓
実際には「存在しないユーザーへのログイン」→ 401
        ↓
assert_eq!(status, 401) は通る
```

**意図していた経路（正しいユーザー・誤ったパスワード）を、もう一度も通っていない。** 未知ユーザーの401は `login_with_unknown_user_returns_401` が既にカバーしているので、この2件は同じことを試す重複になっていた。

登録成功の `assert_eq!` を足して検出できるようにした。**セットアップの戻り値を捨てているテストは、前提が崩れても気づけない。**

### 教訓2: 制約の追加は、テストデータの前提を静かに壊す（#5）

`ws_test.rs` はユーザー名の一意性を確保するために UUID 全体を使っていた（task-30 で409衝突を避けるために入れた対応）。**ユーザー名に上限が無かったからこそ成立していた書き方**で、32文字上限を入れた途端に壊れた。

制約を追加するときは、**その制約が無いことに依存しているコード**を探す。長さ・文字種・一意性はテストヘルパーが暗黙に頼りがちな性質。

### 教訓3: 壊れたテストの数が、変更の影響範囲を教えてくれる
5件が落ちたことで「パスワードは register 以外の4つのテストファイルからも作られている」ことが分かった。**落ちること自体は成功**で、これらが1つも落ちなかったとしたら、そのほうが心配だった。
