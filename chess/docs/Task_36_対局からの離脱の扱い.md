# task-36 対局からの離脱の扱い（切断・ログアウト）

## ゴールと完了条件
- 対戦相手が切断したまま戻らない場合、残ったプレイヤーを勝ちにする
- 明示的なログアウトは猶予なしで敗北にする
- 残っているプレイヤーに、相手の切断と確定までの秒数を見せる
- 対局中はロビーに戻れないようにする
- 完了条件: 猶予60秒を過ぎた対局が終了し、レーティングと履歴に反映されること

## 仕様

| 項目 | 決定 |
|---|---|
| 猶予 | **60秒** |
| 判定の契機 | WebSocket 接続時 + 外部からの定期実行（10分間隔） |
| 片方が離脱 | 残った側の勝ち（`end_reason: "disconnection"`） |
| 両者が離脱 | **引き分け**（`end_reason: "abandonment"`） |
| ログアウトボタン | **猶予なしで即敗北**（対局中は表示しない） |
| 対局中のロビー移動 | 不可（投了すれば戻れる） |
| 相手未参加の対局 | 対象外 |

### 切断とログアウトを区別する理由
ログアウトボタンだけを敗北扱いにすると、**ブラウザを閉じた相手には勝てない**。逃げ得が成立してしまう。一方で切断を即敗北にすると、電車がトンネルに入っただけで負ける。

そこで**切断には猶予を置き、明示的なログアウトには置かない**。ログアウトは本人が「やめる」と操作しているので、回線の都合と区別してよい。

### 対局中はログアウトボタンを出さない
当初は確認ダイアログで警告する形にしたが、**「操作できるが警告する」は中途半端**だった。ダイアログを閉じ損ねる、誤って OK を押すといった経路が残る。操作させなければ問題自体が消える。

「ロビーへ戻る」も同じ理由で消す。戻ってもその対局は進行中のままで、相手は指し手を待ち続ける。

**投了は常に押せる。** これが無いと対局から抜ける手段がなくなり、閉じ込められる。投了すれば `result` が入るので両方のボタンが戻る。

サーバー側の `POST /auth/logout` は残す。**画面から消しても、別タブのロビーからログアウトする経路は塞げない**ため、その場合に対局が残らないようにする安全網として要る。

### 両者離脱を引き分けにした理由
先に切断したほうを負けにする案もあるが、**その場にいない相手を勝者にすると「先に落ちたほうが負け」というレースを生む**。回線が不安定な二人が競って再接続する状況は不健全。両者不在なら勝者なしが素直。

## 構成

```
WebSocket接続            定期実行（GitHub Actions, 10分間隔）
      │                              │
      │  mark_connected              │  POST /internal/sweep
      │  （切断時刻をクリア）          │  （X-Sweep-Token で認証）
      ▼                              ▼
   finish_if_abandoned  ←──────  sweep（advisory lock で1本に）
      │
      ├─ domain::abandon::decide（純粋関数）で判定
      ├─ games を finished に（条件付きUPDATE）
      ├─ rating::apply_rating
      └─ WebSocket に game_over を配信
```

### なぜ外から叩くのか
Render の無料枠はリクエストが無いとスピンダウンするため、アプリ内で `tokio::spawn` したタイマーは**プロセスごと消える**。60秒後に発火するはずの判定が失われ、対局が `in_progress` のまま残り続ける。

ops-hub で採った「常駐スケジューラを持たず、GitHub Actions の定期実行が起動する」実行モデルと同じ構図。**別プロジェクトで決めた設計が、そのまま持ち込めた。**

### 定期実行の間隔が猶予より長くてよい理由
猶予60秒に対して定期実行は10分間隔。一見粗いが、**残っている側が画面を開いていれば WebSocket 接続時に即座に判定される**。定期実行の役割は「誰も見ていない対局の後始末」であり、決着の速さは求められない。

GitHub Actions の `schedule` は混雑時に数分遅れるため、そもそも秒単位の精度は期待できない。

## 設計判断の根拠

### 判定を純粋関数に切り出す
`domain::abandon::decide` は時刻を引数で受け取る。これにより**60秒待たずにテストできる**。境界（ちょうど60秒）や両者離脱の扱いは単体テストで守り、統合テストは「DBの値を読んで終了処理まで進むか」に集中させる。

### 切断時刻を上書きしない
`set_disconnected_at` は `IS NULL` のときだけ書く。上書きすると、**短時間の再接続を繰り返すことで猶予を無限に延ばせてしまう**。

### フラグではなく時刻だけを持つ
「切断中フラグ」と「切断時刻」を両方持つと、片方だけ更新される不整合が起きうる。NULL かどうかが接続状態そのものを表す設計にした。

### 接続数を数える
同じユーザーが2タブ開いていて片方を閉じただけで切断扱いになると誤判定になる。`(game_id, user_id)` ごとの接続数をメモリで持ち、0になったときだけ記録する。

**メモリなので再起動で消えるが、実害は小さい。** 再起動時は全接続が切れ、クライアントが再接続してくれば `mark_connected` でカウントが復元される。

### 条件付き UPDATE で二重終了を防ぐ
`WHERE id = $1 AND status = 'in_progress'` とし、`rows_affected() == 0` なら何もしない。WebSocket 接続時の判定と sweep が同時に走っても、実際に終了させるのは1つだけになる。

### advisory lock はロック専用の接続で取る

`&PgPool` を Executor に渡すと、呼び出しごとに**プールから1本借りて即座に返す**。advisory lock はセッション（物理コネクション）に紐づくため、`pg_try_advisory_lock` を取った接続と `pg_advisory_unlock` を呼ぶ接続が別になりうる。

```
lock を取る   → 接続A を借りて実行 → 接続A をプールへ返却（ロックは接続Aが保持したまま）
sweep_inner   → 接続B, C... を借りる
unlock を呼ぶ → 接続D を借りて実行 → 持っていないロックなので false が返るだけ
                ↓
         接続A がロックを持ったままプールに残る
                ↓
         以後の sweep は永久に「別のプロセスが実行中」→ Ok(0)
```

**しかも `Ok(0)` は成功なので、GitHub Actions からは正常に見える。**掃除が二度と走らないまま、通知も出ない。

`state.db.acquire()` で1本を確保して変数に保持し、lock と unlock を同じ接続で実行する。ロックはその変数が生きている間ずっと保持されるので、`sweep_inner` が間に何本プールから借りても影響しない。

```rust
let mut conn = state.db.acquire().await?;   // 1本だけ確保して保持
// lock / unlock は &mut *conn で、作業は &state.db で
```

これは ops-hub の `run_lock.rs` が `pool.acquire()` で接続を保持している設計と同じ。**同じ問題を一度解いていたのに、こちらでは踏襲できていなかった。**

### sweep に advisory lock を使う
定期実行が重なったとき、同じ対局を二重に処理しようとする。ロックが取れなければ**何もせず成功を返す**。エラーにすると、正常な競合が定期実行の失敗として通知されてしまう。

ops-hub で「ロック競合時は409ではなく200」と決めたのと同じ考え方。

### カウントが0になったらクライアントが判定を要求する
`finish_if_abandoned` は WebSocket 接続時にしか走らないが、**残っている側はすでに接続済み**なので、カウントが0になっても誰も判定を起こさない。次の sweep（最大10分後）まで待たされる。

`POST /games/:id/claim-abandonment` で、接続時の判定と sweep の隙間を埋める。**判定そのものはサーバーが行う**ので、クライアントが時計を進めても猶予前に勝ちにはならない。

### 残り秒数を送る（時刻ではなく）
サーバーが「確定時刻」を送ると、クライアントとサーバーの時計のずれがそのままカウントダウンの誤差になる。**残り秒数なら、受け取った側が「今から N 秒後」として扱えばずれの影響を受けない。**

再接続した人には、接続時に `opponent_grace_remaining` で残りを計算してその接続にだけ送る。ブロードキャストしないのは、他の人には既に届いているため。

### 起動時にマイグレーションを適用する
ローカルDBへの適用漏れで `column does not exist` が起きた。**`sqlx::test` は毎回専用DBに全マイグレーションを当てるため、テストは緑のままローカル環境だけが壊れる。**

起動時に適用すれば、ローカルも Render も漏れが構造的に無くなる。本番へのマイグレーション適用が手動だった問題（task-24 の手順）も同時に解消する。Render の無料枠は単一インスタンスなので、複数プロセスが同時に走る心配はない。

### sweep を OpenAPI に載せない
利用者向けの API ではなく運用用。公開仕様に混ぜると「このアプリの使い方」が読みにくくなる。`EXPECTED_PATH_COUNT` も変更不要。

### 共有シークレットで認証する
呼び出し元が利用者ではなく CI なので JWT ではない。**運用用のユーザーを作ってトークンを発行させると、その資格情報が通常のログインにも使えてしまう。**

比較は定数時間で行う。長さが違えば即 false を返しているが、これは長さが漏れるだけで内容は漏れない。

### 1局の失敗で sweep 全体を止めない
`sweep_inner` は各対局のエラーをログに出して次に進む。1局の異常で残り全部が処理されないほうが影響が大きく、失敗した対局は次回の実行で再度拾える。

## つまずいた点と教訓

### 単一スレッドのテストでは再現しないバグだった
上記のロック解放漏れは、`sweep_finishes_multiple_games` を通過していた。低負荷ではプールの空き接続が使い回され、**たまたま lock と unlock が同じ接続に当たる**ため。

修正にあたり、`sweep_releases_the_lock_for_the_next_run` を追加したうえで**あえて旧実装に戻し、5回連続で失敗することを確認した**。`sweep_inner` が間に何度もプールへアクセスするので、たまたまではなく毎回再現する。

**新しいテストは、直したはずのバグで赤くなることを確かめて初めて意味を持つ。** 確認しないと「たまたま通っていたものが、たまたま通り続けている」状態と区別がつかない。このテストは `pg_locks` を直接見て、sweep 終了後にロックが残っていないことと、2回目の sweep が機能することの両方を検証している。

### `opponent_joined` で `status` を更新していなかった
対局作成者（白番）だけ、ボタンの表示制御が効かなかった。`GamePage` が `opponent_joined` イベントで `black_user_id` だけを更新し、`status` を `"waiting"` のまま残していたため。

```diff
- setGame((prev) => (prev ? { ...prev, black_user_id: event.user_id } : prev));
+ setGame((prev) =>
+   prev ? { ...prev, black_user_id: event.user_id, status: "in_progress" } : prev
+ );
```

**途中参加した側（黒番）は初回取得で `status: "in_progress"` が返るので再現しない。** 役割によって出方が変わるため、片方だけで試すと見逃す。

**教訓**: WebSocket イベントでサーバーの状態変化を反映するとき、**変化した項目を全部反映できているか**を確認する。サーバー側では1回の操作で複数のカラムが変わっているのに、フロントは1つしか更新していないことがある。

### 誤った指摘を検証で覆した
`0x5357_4545` という SQL リテラルについて「Postgres には 0x 記法が無いので構文エラーになる」という指摘があったが、**PostgreSQL 16 は SQL:2023 準拠として16進・8進・2進リテラルとアンダースコア区切りをサポートしている**。`psql` で直接実行して確認した。

ただし本番の Neon が同じバージョンとは限らないため、バインドパラメータ `$1` に変更してバージョン依存を無くした。**指摘は誤りだったが、対応した結果は改善になっている。**

### advisory lock のスコープを確認した
advisory lock は**データベース単位**でスコープされ、クラスタ全体では共有されない。`sqlx::test` はテストごとに別 DB を使うため、`SWEEP_LOCK_ID` が固定値でも並列テスト間で衝突しない。

固定のロックIDを使うときは、**同じIDを使う他の箇所が無いか**と**スコープがどこまでか**の2点を確認する。
